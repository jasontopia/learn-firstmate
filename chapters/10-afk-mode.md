# 第 10 章：afk 离席模式

## 这一章讲什么

第 9 到 11 章是规模、离席、以及「到底是哪个工具在跑你的船员」这类进阶话题。这一章讲的是其中的离席部分：你（船长 / captain）不可能一直守在屏幕前，但一支队伍不能因为你走开就没人管。这一章要解决的问题是四件事：你离开键盘期间谁接手监督、你说出「离席」这句话本身算不算已经生效、离席期间大副 / firstmate 敢凭你留下的话往前走到什么程度，以及最重要的一条 - 遇到真正伤筋动骨的选择时它依然会不会停下来等你、你回来时它又怎么先把这段时间发生的事交代清楚。

本章依据的权威文件是 `AGENTS.md` 第 8 节「Supervision protocol」中的「Away-mode and quiet-mode stub」小节，以及 `/afk` 技能自身的说明。这个教程仓库到目前为止船长一直在场，还没有真的用过离席模式，所以本章不会讲一个「真实发生过的案例」，全部依据原文和类比来讲；如果用到具体场景，会明确标注是假设。

## 离席期间谁在盯着：不是没人管，是换了一套机制

原文写得很直接：

> While `state/.afk` exists, the daemon owns supervision; do not arm a separate watcher.

翻成大白话：你说走开之后，监督这件事不会停摆，而是从「你在场时那一套盯着队伍的机制」切换成一个专门的守护进程 / daemon。这个 daemon 是唯一在管的那个 - 大副不会因为你走开就额外再武装一个 watcher 来做同样的事，一件事只由一个机制盯着。你走开留下的是一支依然有人看着的队伍，只是看着它的角色换了。

## `/afk` 这句话本身就是行动的开始，不用再等一次确认

前几章遇到的大多数场景里，你说一句话，大副会先讲清楚它打算怎么做，再动手 - 这是第 2 章讲过的「先立项、边界说清楚」的节奏。离席模式不一样。原文：

> `state/.afk-contract` is the away posture, written in the same turn as `/afk` before any other work, because `/afk` is itself the go: no read-back gates entry or waits for a go; entry announces hold-for-return only, and the away session acts on those words by its own judgment through the guarded scripts under standing authority, holding for the return on doubt.

拆开看：你说出 `/afk` 连同你交代的那几句话，这件事本身就是「开始执行」的信号，不是「请求批准」的信号。大副会在同一个动作里，把你说的话原样记成一份留存的记录，在做任何别的事之前先记下来 - 因为等你确认，你可能已经真的走开、看不到屏幕了。它随后会把记下来的内容念给你听一遍，但这一步只是核对「我记的对不对」，不是在等你点头，记录本身在你说完那一刻就已经生效。

## 离席期间它敢自己往前走到什么程度

同一段原文的后半句给了边界：大副「acts on those words by its own judgment through the guarded scripts under standing authority, holding for the return on doubt」- 靠已有的、被认可过的脚本和流程去做事，用自己的判断去认，你留下的那句话在眼下这件事上算不算数，拿不准的时候就按兵不动、等你回来。

这里有两层意思容易混在一起，需要拆开：第一层，它能用的手段是「guarded scripts under standing authority」- 也就是本来就被允许使用的、带着护栏的既有流程，不是临时现编一套新做法；第二层，你留下的那句话到底覆盖不覆盖眼下这件事，由它自己判断，不是机械匹配关键词。判断不准的时候，答案永远是「等你回来」，而不是「反正问题不大，我自己拿主意」。

## 红线不会因为离席而放宽

这是这一章最重要的一条，原文写得毫不含糊：

> Away and quiet mode never expand approval authority for merges, ask-user findings, destructive actions, irreversible actions, or security-sensitive choices.

也就是说，离席（`/afk`）和静默（`/quiet`）这两种姿态，改变的只是「你怎么被告知」和「一个原本要问你的节点现在怎么处理」，从来不会让大副对合并、ask-user 发现、破坏性动作、不可逆动作、涉及安全的选择这几类事拥有比你在场时更大的权限。`/afk` 技能自己的说明里也把这条线重复了一遍，说得更直白：不管你走之前那句话怎么说，这几类动作都不能被预先授权。换句话说，哪怕你临走前明确交代过「这种情况你就自己去改」，只要这件事落在这几类里，大副依然会把它留着等你，而不是拿你那句话当挡箭牌往前冲。离席解决的是「谁盯着」和「一般性的活怎么往前推」，不是把这几道闸门也一并交出去。

## 船长回来了：先交代清楚，再干活

那大副怎么知道你回来了？原文给的判断标准很朴素：

> A marked message while away or quiet mode is active is internal escalation and does not exit that mode. Any other unmarked message means the captain returned in away mode (load `/afk`, run the return owner, and do not process that message as ordinary work until its durable catch-up gate clears)... Bias ambiguous input toward exit because a present captain takes precedence.

翻译过来：大副能分清两种消息。一种是它自己那套监督机制内部产生的、带着特定标记的消息 - 这种不算你回来，离席姿态原样继续。另一种是任何不带这种标记的普通消息 - 哪怕只是随口一句话，不带 `/afk`，也一律当成「你回来了」。而且规则明确偏向「就当你回来了」：拿不准的时候，宁可当你已经回来，也不要因为省一次交接就继续把你当成不在场 - 一个走了眼的判断，大不了你再说一次 `/afk` 纠正回来，代价很小；反过来把已经回来的你继续当成不在场，代价要大得多。

判断出你回来之后，大副不会直接就着你那句随口的话开始干活，而是先跑一遍返场流程，把离席期间发生的事交代清楚 - 这道交接闸门清完之前，你带回来的那句话不按普通工作处理。打个比方（下面这段是**假设**的场景，不是这个仓库里真实发生过的事）：假设你交代完一句「你按流程正常推」就走开了，回来后你只是问了句「现在几点了」- 大副不会先答「现在几点」，而是先说清楚这段时间队伍做了什么、还有哪些事在等你，交代完之后才轮到回答你那句「现在几点」。这就是「先交代清楚再继续干活」的意思。

## 动手练习

下面的练习是**只读且不可执行**的：只是让大副就着一个假设场景做推演、把规则讲清楚，不会真的创建或改动 `state/.afk-contract`、`state/.afk` 这类运行状态文件，不会真的运行 `/afk` 或任何相关脚本，不会派出真正的船员，也不会改动任何被版本追踪的文件。你随时可以停下。

做练习前，先在你的 FirstMate 目录里启动一个 primary 会话，这样你面前的这个 agent 就是你的大副。

### 练习：推演一次离席场景，不真的进入离席姿态

对大副说：

> 大副，我想跟你推演一次离席模式的规则，不是真的要你进入离席姿态：请不要创建或改动 `state/.afk-contract` 或 `state/.afk`，也不要真的运行 `/afk` 或任何相关脚本。假设我刚才对你说了这样一句话：「/afk，如果有活已经走完质检流水线，你就按原来的节奏正常往下推进就行，其他一切都留着等我」。请你不要真的执行这句话，纯粹在纸面上帮我推演，回答四个问题：一，这段时间谁在替你盯着整支队伍；二，我刚才那句「/afk...」本身是不是要先经过你确认、等我点头才算数，还是我说完那一刻就已经生效了；三，如果这期间真有一件活走完了质检流水线，你会怎么处理，如果同一时间又冒出一个必须靠强制推送、覆盖掉别人已提交历史才能推进的情况，你会不会因为我说了「你就按原来的节奏推进」就去做；四，假设推演到这里结束，我之后随口发一句不带 `/afk` 的普通话，比如「现在几点了」，你会怎么处理这条消息 - 是直接回答，还是要先做点别的。

**预期会看到什么**

- 第一句：它会说这段时间由一个专门的守护机制（daemon）接管监督，而且不会再另外武装一个 watcher 去做重复的事。
- 第二句：它会说这句话在我说完那一刻就已经生效、已经被记下来了，不等我确认；它随后的复述只是把记下来的内容念给我听、核对有没有记错，不是在等我点头。
- 第三句：对「已经走完质检流水线、按原来节奏正常推进」的情况，它会说这属于我离席前那句话已经覆盖、走的也是既有的、被认可的流程，所以它会凭自己的判断往前推，不会为这个专门跑来问我；但对「需要强制推送、覆盖别人历史」这种破坏性且不可逆的操作，它会明确说这条线不会因为我说了「你就按原来的节奏推进」就被放开，依然会停下来把它留着等我回来处理。
- 第四句：它会说自己先要把离席期间发生的事交代清楚（一份交接），交代完之后才会把「现在几点了」当成一个普通问题来回答 - 不会一上来就直接回答；它还会指出，如果换成是它自己监督机制内部产生、带着内部标记的消息，那不算我回来，不会触发这段交接。
- 四个回答都会点出处：`AGENTS.md` 第 8 节「Away-mode and quiet-mode stub」小节，以及 `/afk` 技能自身的说明。

**怎么判断做成了**

四点都满足才算：第一句准确讲出「daemon 接管、不另外武装 watcher」；第二句准确讲出「/afk 这句话说完即生效，不等确认」而不是「它需要先跟我确认了才算数」；第三句既讲对了「已授权范围内的活可以凭判断继续推」，又讲对了「破坏性/不可逆操作不会因为你的话被放开」这条红线 - 少了后半句就是没做成；第四句准确讲出「先交代清楚，再回答」而不是直接就手回答你的新问题。以及 - 最关键的一条 - 它**没有真的创建或改动任何 `state/.afk` 相关文件，也没有真的运行 `/afk`**，这段推演从头到尾只停留在对话里。

文件层面的验证办法跟前几章一样，**前后对比**：提问之前在 FirstMate 目录里跑一次 `git status --short` 和 `git diff HEAD`，把两份输出都留着；问完之后再各跑一次，两次应该完全一样。`state/` 是大副私有的运行状态，被 gitignore 掉了，这两条命令本来也看不见，会话期间它会不会被真的写入不影响这两条命令的输出，但你依然应该在对话里确认大副没有说自己创建或改动了 `state/.afk-contract`、`state/.afk` 这类文件。

如果它说离席期间「没人管，等你回来再说」，或者说那句 `/afk` 要先经过你确认才算数，或者认为你交代过「你就按原来的节奏推进」之后连强制推送覆盖历史这种事也可以自己做，或者收到你那句普通话后直接就回答而不先交代离席期间发生了什么，那就是没做成。
