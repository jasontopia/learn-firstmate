# 第 7 章：待办队列与船长决策

## 这一章讲什么

前面几章跟着一件活走。实际上大副 / firstmate 手上从来不止一件活，这些活要记下来、排好队。其中有一类很特别：不用船员 / crewmate 改任何代码，只要船长 / captain（你）说一句话。

这一章讲三件事：待办队列（backlog）怎么把活分成在办、待办和已完成；一个等你拍板的问题，为什么也只是一张工单，只是被挂起（hold）等你；你的回答怎么把它关掉。大副怎么盯住整支队伍、什么事会叫醒它，是下一章的内容。

本章依据 FirstMate 仓库 `AGENTS.md` 第 10 节「Backlog contract」、`docs/configuration.md` 的「Backlog backend」一节，以及 `bin/fm-captain-hold.sh` 开头的注释。

## 待办队列：活分三类

待办队列是整支队伍所有活的长期记录，用 `tasks-axi` 管理，默认存在 `data/backlog.md`。它只记活，不记人：常驻的二副 / secondmate 不会作为一条工单出现在队列里。队列里的每一条是一件事。

每件活都在下面三类之一：

- **待办**（`## Queued`）：已经登记了工单，还没派出去。
- **在办**（`## In flight`）：已经派了船员，正在工作树里干。
- **已完成**（`## Done`）：已经做完，只保留最近几条。

在自动挪动工单的机制生效时，从待办到在办、从在办到已完成，这两步不用大副手动去改（什么时候生效、有什么例外，见 `docs/configuration.md`）。派船员的 `bin/fm-spawn.sh` 和收尾清理的 `bin/fm-teardown.sh` 会自己挪动工单；挪不成功，它们会拒绝继续，不会报告「已经派出去了」或「已经做完了」。

所以大副要自己做的只剩三件：派工前登记工单，记录决定，保持工单备注是最新的。另外，每次有活收尾清理完，或者每次心跳检查时，大副都会回头看一遍待办的活，把依赖和时间条件都满足了的派出去。队列不是一张放着不动的清单，有变化就要重新过一遍。

## 等你拍板的问题，也是一张工单

第 10 节的原话是 "A decision is simply a task held for the captain."：一个决定就是一张挂起等船长的工单。

决定没有单独的类型。它不是队列外的另一种东西，也不是聊天记录里说过就算。它就是一张普通工单，只是被挂起等你回答。所以一个等你拍板的问题，和一件等船员去改代码的活，记录方式完全一样：会出现在队列里，会被跟踪，不会因为「只是问一句」就被漏掉。

具体做法分两步：

1. **还没有对应的工单，就先用 `bin/fm-tasks-axi.sh add` 登记一张。** 如果这个问题卡住的是一件正在做的活，就直接挂起那件活，不另开新工单。`bin/fm-captain-hold.sh` 的注释写着："Prefer holding the work item the question gates over minting a new row."
2. **然后一定要用 `bin/fm-captain-hold.sh hold <id> --reason "<原因>"` 挂起它。** `--reason` 写清为什么这件事要你来定。你暂时不想回答、要过一阵再看，就加上 `--until <日期>`，把「以后再说」变成一个具体日期，而不是一张一直挂着、没人知道什么时候该回头看的工单。

还有一种情况：有些事不属于哪个项目的具体任务，比如你和大副对话里一个待你决定的问题，或者一条要转告你的提醒。只要值得长期跟踪，也要单独登记一张工单，用同样的方式挂起，不能只留在某次对话里。

## 挂起后，工单里记了什么

按 `bin/fm-captain-hold.sh` 的注释，`hold` 会在工单正文里记一个 UTC 时间戳「Captain hold set:」。重复挂起同一张工单，原来的时间戳不会被覆盖；一件活解除挂起后又被挂起，算一次新的等待。已经关掉的工单不能再挂起，会被拒绝。

这些细节都是为了让记录如实反映经过，不会每操作一次就把之前的痕迹抹掉。以后回头看一个决定是怎么走的，看到的是真实的时间线。

## 你的回答怎么关掉它

`bin/fm-captain-hold.sh` 的 `answer` 子命令会记下你的原话，并在同一步里把这件事了结：记录你的回答和关闭工单是同一个动作，不用再有人去手动关一下。

分两种情况：

- 挂起的是**专门为等你拍板而登记的工单**（比如「要不要给这个仓库配 CI」，本身不需要船员干活），你的回答一记下，工单就用 `tasks-axi done` 关掉，进入已完成。
- 挂起的是**一件正在做、只是卡在等你判断的活**，就用 `answer --release`：只解除挂起（`tasks-axi unhold`），让这件活接着做，不把它标成完成，因为活本身还没干完。

## 例子：这个仓库的 CI 是怎么来的

这个仓库自己的历史里，有一段能公开核对的经过，正好串起了这几件事。

交付第一章时，质检流水线走到 CI 那一步，但仓库里还没有任何 CI 检查，PR 上的检查列表是空的，流水线等不到检查通过。要不要给一个纯文档仓库配 CI，是一个该由船长定的产品问题，船员不能自己拍板。当时挂起写的 `--reason` 和船长回答的原话，是大副私有的记录，不在这个仓库的 GitHub 历史里，教程不去猜。

能公开核对的是结果：[PR #2「ci: 加一套零依赖的 markdown 链接与格式检查」](https://github.com/jasontopia/learn-firstmate/pull/2)比[PR #1「docs: 搭建教程骨架并写出第一章《FirstMate 是什么》」](https://github.com/jasontopia/learn-firstmate/pull/1)先合进 `main`。按上面的规矩倒推：那次挂起先被船长的回答关掉，接着有了 PR #2 这件新活去配 CI；CI 配好合并后，卡住的第一章才重新跑通，作为 PR #1 合并。这就是编号在前的 PR #1 反而要等 PR #2 先合并的原因。

## 动手练习

这个练习是只读的：只让大副读队列和工单并汇报，不登记工单，不派船员，不改被 git 追踪的文件。

开始前，在你的 FirstMate 目录里启动一个主会话，这个会话里的 agent 就是你的大副。

### 练习：读一遍你的队列，找出挂起的工单

对大副说：

> 大副，不用派船员，帮我读一遍现在的待办队列：在办和待办各有哪些活，各是什么情况；有没有工单正挂起等我拍板，有的话，每一张为什么挂起、给了我哪些选项、在等什么。如果队列是空的，或者没有挂起的工单，就直接说没有，不要编一个出来。只读现状，不要登记工单，也不要改任何东西。

**你应该看到**

- 按在办、待办、已完成分开讲，而不是把所有工单混在一起。
- 每一张挂起的工单，都说清挂起的原因（也就是 `--reason` 里写的）和需要你回答什么，而不是只说「有件事在等你」。
- 没有挂起的工单时直接说没有，不会凑一个像决定的东西出来。
- 说明出处：`AGENTS.md` 第 10 节「Backlog contract」，并说明它读的是 `tasks-axi`（或 `bin/fm-tasks-axi.sh`）给出的实际队列，不是凭印象讲。

**怎么检查**

- 讲的是队列的真实状态。你可以自己用 `bin/fm-tasks-axi.sh` 或打开 `data/backlog.md` 对照，看是不是真有这些工单。
- 如果它说某张工单被挂起了，你追问「这真的写在那张工单里吗」，它的回答站得住。
- 跟第 1 章一样，提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样。

如果它顺手替你回答了某张挂起的工单，或者登记了一张新工单，就算没做成。这个练习只要它读和讲。
