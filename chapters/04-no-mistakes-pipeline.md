# 第 4 章：no-mistakes 质检流水线

## 这一章讲什么

第 1 章说过，选了 `no-mistakes`，代码审查、修复、测试、文档、推送、开 PR、CI 就全部由它负责；发现的问题由流水线自己修，船员只在流水线停下来等回复时作答。第 2 章讲了交付方式是在立项时定的。这一章专门讲这条质检流水线：它自己能修到什么程度，什么时候会停下来问人，以及轮到大副 / firstmate 决定时，它按什么规矩答。

本章依据 FirstMate 仓库 `AGENTS.md` 第 7 节的「Selected delivery path and merge authority」和「Validate」两个小节，以及 `ask-user-authority` 技能（`.agents/skills/ask-user-authority/SKILL.md`）。`AGENTS.md` 要求大副在处理 ask-user 类问题前先读这个技能，具体怎么判断只写在那里。

## 流水线管什么

`AGENTS.md` 第 7 节规定：选了 `no-mistakes`，审查、修复、测试、文档、推送、PR、CI 就全部由它负责，不再另加人工审查。

流水线发现的问题，只要它自己判断得出该怎么改，就自己改、自己提交，然后接着往下走，不用等船员，也不用等你。

## 什么时候它会停下来

有一类问题流水线不自己拿主意，叫 ask-user 类问题。遇到这类问题，这次运行会停在 `needs-decision`，等人来决定。

这个决定不归船员。`AGENTS.md` 第 7 节「Validate」规定：启动这次运行的船员负责一路调用 `no-mistakes axi run` 和 `no-mistakes axi respond`，直到下一个停顿点或出结果；但 ask-user 类问题船员不能自己答，要原样交给大副。干活的人从不回答自己这件活里冒出来的 ask-user 类问题。反过来，大副也从不替船员调用 `no-mistakes axi respond`，它只把决定告诉船员，由船员去回复。

## 大副怎么答：自己定，还是来问你

大副不是想怎么答就怎么答。`ask-user-authority` 的规矩是：跟已确认的设计方向一致、答案明确的问题，大副自己定；只有真正拿不准、会扩大范围、或者有破坏性的问题，才来问你。

「已确认的设计」指这件活已经定下的要求：任务简报里的船长意图、你后来补充的话，再加上大副规格。大副拿它当尺子，不凭感觉。只有下面几种情况会来问你：

- 这个修复会明显扩大这件活要交付的东西：多出一项新的保证、一个新子系统、一层新抽象、一个新的兼容面、一项持续监控要求之类，而原来的要求里没有。
- 这是一个产品或架构上的选择，原来的要求里没定过。
- 同一类问题反复出现，一轮轮修补只是在给一个有问题的设计打补丁，而不是在修各自独立的缺陷。
- 这个选择有破坏性、不可逆，或者真正涉及安全。

其他情况大副都自己定，哪怕修起来很复杂：只要是原来要求范围内的直接修正，就不来问你。

定下之后，大副给船员一条明确的指示：对应哪条决定记录、哪一步、批准还是别的动作、涉及哪几个问题编号，需要时附上具体做法，以及船员要执行的那条 `no-mistakes axi respond` 命令。这条指示一送到，船员那边对应的决定记录就关掉了（靠的是 `--resolve-key`）。

## 一个真实的例子

写第 2 章的那件活用的就是 `no-mistakes`。那次运行在 test 这一步停下来问了一个 ask-user 类问题：这次改动只有 markdown 文档，没有能实际运行起来验证的界面，要不要跳过现场验证继续？

大副判断这个问题不扩大范围：不要求新的保证或子系统，不是没定过的产品选择，也不涉及破坏性或不可逆的操作，只是文档改动确实没有能跑起来的界面。按 `ask-user-authority`，这属于答案明确、跟已确认设计一致的问题。所以大副自己批准，让船员执行 `no-mistakes axi respond --step test --action approve --reason '...'`，没有来问船长。

## 动手练习

两个练习都是只读的：只让大副推演和汇报，不启动 no-mistakes 运行，不登记工单，不派船员，不改被 git 追踪的文件。

开始前，在你的 FirstMate 目录里启动一个主会话，这个会话里的 agent 就是你的大副。

### 练习 1：用两个假设的问题测试大副的判断

对大副说：

> 大副，我想看看你遇到 no-mistakes 的 ask-user 类问题时怎么判断，不是真要你跑流水线。假设有两个问题，都是编的，不用去查任何正在做的活。第一个：「测试发现一个已确认的设计里本来就该覆盖的边界情况没覆盖，要不要现在补一条回归测试？」第二个：「审查建议给这个功能加一套全局的持续监控和告警系统，原来的验收标准里没提过。」请分别说你会自己定还是来问我，为什么。只推演，不要启动 no-mistakes，也不要派船员。

**你应该看到**

- 第一个，它自己定：这是已确认设计范围内的直接修正，不扩大范围。
- 第二个，它来问你：这加了一个原来没要求的子系统和持续监控要求，扩大了范围。
- 判断依据是「会不会扩大这件活要交付的东西」，而不是笼统的「这个复杂」「这个简单」。
- 说明出处：`ask-user-authority` 技能。

**怎么检查**

- 两个判断方向都对：第一个自己定，第二个来问你。
- 理由落在「范围有没有被扩大」上。
- 没有启动 no-mistakes 运行，也没有多出新的船员窗口。
- 跟第 1 章一样，提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样。

如果它说第二个也可以自己定，或者真去跑了一次 no-mistakes，就算没做成。

### 练习 2：回看一次真实的 ask-user 决定

对大副说：

> 大副，回头看第 2 章那件活交付时，no-mistakes 在 test 这一步问过的那个 ask-user 类问题：改动没有能实际运行起来验证的界面，要不要跳过现场验证。讲讲你当时按 ask-user-authority 怎么判断是自己定还是来问我，依据是哪几条，最后给船员的指示是什么。如果记录已经找不到了，就直接说找不到、为什么，不要编。不要改文件，也不要派船员，只讲已经发生的事。

**你应该看到**

- 讲的是这件真实的事，带着你能核对的信息，比如对应的 PR，或者当时让船员执行的 `no-mistakes axi respond` 命令。
- 明确说出判断依据：不扩大范围，不是没定过的产品选择，不是反复出现的同类问题，不涉及破坏性或不可逆的操作。而不是笼统一句「这个可以自己定」。
- 如果记录找不全，它会直接说找不到并说明可能的原因，不会编一段判断过程。

**怎么检查**

- 讲的是能核对的真事，判断依据对得上 `ask-user-authority` 的规矩。
- 找不到记录时承认找不到。
- 提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样，也没有多出新的船员窗口。

如果它打算真去跑一次 no-mistakes，或者在找不到记录时编了一段判断过程，就算没做成。
