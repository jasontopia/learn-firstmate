# 第 1 章：FirstMate 是什么

## 这一章讲什么

FirstMate 把你和一群编码 agent 的协作分成三个角色。弄清谁负责什么，你就会明白它为什么不自己改代码、为什么合并前一定要问你。

这一章讲三件事：三个角色各管什么；最重要的四条规矩；一件活从你提出到合并要经过哪几步。最后有两个只读的练习。

本章依据 FirstMate 仓库里的 `AGENTS.md`（主要是第 1 节的硬规矩和第 7 节的任务流程）、`README.md`，以及几个 `bin/` 脚本开头的注释。想核对细节，可以直接去读这些文件。

## 三个角色

FirstMate 借用了船上的称呼。

### 船长 / captain：你

船长就是你本人。`AGENTS.md` 开头写着："You are the first mate. The user is the captain."

你负责：

- 说清楚要做什么。
- 在关键的地方拍板，特别是合并，以及有破坏性、不可逆或涉及安全的操作。
- 决定每个项目用哪种交付方式、合并前要不要先问你。

你不用盯进度，不用在一堆终端之间来回切，也不用记哪个窗口在做哪件活。这些都交给大副。

### 大副 / firstmate：你唯一的对话对象

你所有项目上的软件工作，都只跟大副说。它负责：

- 判断这件活属于哪个项目，是直接改，还是先调查清楚。
- 登记工单，给船员写任务简报（brief）。
- 派船员干活，每个船员一个独立的 git 工作树（worktree）。
- 盯着整支队伍把活干完，只在真正需要你决定时才来找你。
- 用简单的话告诉你结果：一个 PR、一次你批准过的本地合并，或者一份调查报告。

大副自己不改项目代码，原因见下面的规矩一。

### 船员 / crewmate：动手干活的人

船员是大副派出去的 agent，一人负责一件活。每个船员有自己的会话窗口（比如一个 tmux 窗口或 Herdr 标签页，你随时可以看，也可以直接在里面打字）和自己的工作树。

船员负责：

- 在自己的工作树里改代码、跑测试、写文档。
- 启动质检流水线，流水线停下来等回复时由它作答。
- 通过流水线开 PR。
- 把进展报告给大副。

船员不决定合并，也不直接找你说话。

## 四条硬规矩

`AGENTS.md` 第 1 节按优先级列了五条硬规矩（hard rules）。这里讲对新手影响最大的四条。

### 规矩一：大副不改项目

原文是 "Never write to a project."。大副只读项目，不在项目里编辑、提交，也不运行会改变项目状态的命令。改项目是船员的事。

例外很少，而且都有严格限制，比如你当场明确批准的某个具体操作。即使在例外情况下，也不允许强推，不允许丢弃还没合入的工作。

为什么这样定：大副亲手改的代码，没有独立的工作树，不经过质检流水线，也没有 PR 审查。把大副挡在代码外面，每一处改动就都得走同一条有检查的路。另外，大副要在多件活之间排优先级、处理冲突，它自己手上没有改动，判断才公正。

### 规矩二：你不点头，就不合并 PR

原文是 "Never merge a PR without the captain's explicit word."。

唯一的例外是你给某个项目打开了 `yolo` 开关。打开后，大副可以自己合并 CI 全部通过、而且没超出任务范围的 PR。但即使打开了 `yolo`：

- CI 没通过的 PR 仍然不合，除非你当场明确放行某一项具体的检查。
- 有破坏性、不可逆或涉及安全的合并，仍然要问你。

`yolo` 只管合并权限，跟用哪种交付方式无关。

为什么这样定：合并之前的每一步都能重来，工作树可以扔，提交可以改，PR 可以关。一旦合进主分支，别人就会在它上面接着干活，很难再撤回。所以前面的步骤可以交给自动化，要不要合由人来定。

### 规矩三：不删还没合入的工作

原文是 "Never tear down unlanded work."。没提交的改动一律算没合入。一件活有没有合入，由收尾脚本 `bin/fm-teardown.sh` 判断。它发现还有没合入的东西，或者确认不了，就会拒绝清理。

清理被拒绝时，要停下来查清楚原因，不要想办法绕过去。只有你明确同意丢弃这些工作，才能强制清理。

为什么这样定：同时跑很多件活，最怕的是东西悄悄丢了。做错了总会有人发现；丢了，你还以为活已经干完了。拒绝清理的代价只是多看一眼，误删的代价却无法挽回。

### 规矩四：船员不直接找你

原文是 "Crewmates never address the captain."。船员有什么事都先告诉大副。

为什么这样定：你能同时跑好几件活而不被打扰，是因为只有大副一个人来找你。要是每个船员都能直接找你，你又回到了同时盯好几个终端的状态。

反过来，你可以直接在某个船员的窗口里说话。大副会把这当作你的指示，并在下一次检查时据此调整。

## 一件活是怎么走完的

拿「写这本教程的第一章」这件活举例，这一章最早就是这样写出来的。

### 第 0 步：你提出要求

你告诉大副：这个仓库叫 Learn FirstMate，是给 FirstMate 新手用的，写成中文教程加动手练习；这次先搭好框架，写出第一章，讲清三个角色和一件活的完整流程。

你只说了想要什么，没说文件叫什么、分几节、用什么格式。这些留给后面的步骤决定。

### 第 1 步：大副分析，登记工单

大副要做这几件事（`AGENTS.md` 第 7 节）：

- **确定项目。** 你点名了项目，就用它；接着上一件事往下说，就沿用上一件的项目；都没有，就拿你的话去比对已登记的项目、正在做的活和项目内容。只有一个项目明显对得上时，直接开始，并告诉你选的是哪个；拿不准就问你一句。
- **确定任务类型。** 默认是交付任务（ship），产出对项目的改动。另一种是调研任务（scout），只产出一份报告，不开 PR。写第一章要往仓库里加文件，所以是交付任务。
- **确定交付方式和合并权限。** 这件活用 `no-mistakes`（完整的质检流水线）交付，`yolo` 关着，所以合并前要你同意。这两项在一开始就定好，后面的步骤不会自己去猜。
- **登记工单。** 这件活进入待办队列（backlog）。
- **写任务简报。** 简报从固定模板（`bin/fm-brief.sh`）生成，其中的任务部分由大副填两块：「船长意图」（Captain's intent）记你的原话和你提的限制，「大副规格」（Firstmate spec）写具体怎么做。两块分开写，是因为质检流水线会拿「船长意图」当验收标准。

### 第 2 步：派船员到独立的工作树

大副用 `bin/fm-spawn.sh` 派出船员。派工时会检查：船员拿到的必须是一个独立的工作树，不能是大副自己用的主仓库目录。检查不通过，这件活就停下来，不会退而求其次在主仓库目录里干（`AGENTS.md` 第 7 节）。

船员启动后会自己再检查一遍（`AGENTS.md` 第 11 节）：当前目录确实是这件活专用的工作树。确认之后才建分支，开始干活。

每件活一个工作树，好处有两个：

- 同一个仓库上的几件活可以同时做，互不干扰。改到同一个文件不算排队的理由，只有真正互相依赖这类情况才需要一件一件来（`AGENTS.md` 第 7 节）。
- 一件活搞砸了，影响只限于它自己的工作树。

### 第 3 步：质检流水线

船员提交完改动后，大副让同一个船员启动 `no-mistakes` 流水线。选了 `no-mistakes`，代码审查、修复、测试、文档、推送、开 PR、CI 就全部由它负责，不再另加人工审查（`AGENTS.md` 第 7 节）。

发现的问题由流水线自己修。船员不自己动手改，只在流水线停下来等回复时作答。

流水线有时会提出 ask-user 类问题，也就是需要人来决定的问题。这类问题船员不能自己回答，要交给大副。大副要么自己决定，要么再来问你。

### 第 4 步：开 PR，等你同意

流水线推送分支、开 PR，然后盯着 CI。CI 第一次全部通过时，船员就向大副报告，附上 PR 的完整 `https://` 链接。

`yolo` 关着，所以到这里就停下，等你决定。

大副用 `bin/fm-pr-check.sh` 登记这个 PR，开始定期查看它有没有被合并。然后告诉你三样东西：PR 链接、一句话结论、`no-mistakes` 给出的风险等级。

### 第 5 步：你同意，合并

你说「合了」，这就是明确的授权。

大副用 `bin/fm-pr-merge.sh` 合并。这个脚本会记录合并信息；如果确认不了合并真的成功，它会拒绝，不会当作已经合入。

### 第 6 步：收尾清理

确认已经合入后，大副才清理这件活：归还工作树，关掉会话窗口，清掉临时状态，把工单标记为完成。清理被拒绝的话，就按规矩三停下来查。

清理完，大副会再看一遍待办队列，把之前被卡住、现在可以开始的活安排上。

## 动手练习

两个练习都是只读的：让大副读资料、讲给你听，不改任何仓库。

开始前，在你的 FirstMate 目录里启动一个主会话（比如运行 `claude`），这个会话里的 agent 就是你的大副。

### 练习 1：问大副它的边界

对大副说：

> 大副，讲讲你自己的边界：你能对我的项目做什么、不能做什么，有哪几条硬规矩，各自为什么存在。说明你依据的是哪个文件的哪一节。不要改任何文件，只回答。

**你应该看到**

- 它用自己的话讲清楚边界，而不是大段贴 `AGENTS.md` 原文。
- 讲到这几条：不改项目代码；你没同意就不合并 PR；不删还没合入的工作；船员不直接找你。
- 说明出处，主要是 `AGENTS.md` 第 1 节。
- 至少称呼你一次「船长」（或 captain）。`AGENTS.md` 要求大副在每条聊天消息里都这样称呼你。

**怎么检查**

提问之前，在 FirstMate 目录里运行 `git status --short` 和 `git diff HEAD`，把输出存下来；问完再运行一次。前后输出一样，就说明大副没改任何被 git 追踪的文件。

两条命令都要跑：`git status --short` 只列出哪些文件有改动，如果大副改的正好是你本来就改过的文件，前后看起来一样；`git diff HEAD` 会列出具体内容，能看出区别。

工作区不必是干净的，你自己可能本来就有没提交的改动，只要前后一致就行。`data/`、`state/`、`config/`、`projects/`、`.no-mistakes/` 这几个目录是你本机私有的，已经被 gitignore，会话期间有写入是正常的，上面两条命令也看不到它们。

如果它贴了一大段原文却没有自己的总结，或者顺手改了文件，就算没做成。

### 练习 2：用一件真实的活对照流程

这个练习需要待办队列里至少有一件活。如果你刚装好 FirstMate，队列还是空的，就先跳过，等做完第一件真实的活再回来。

对大副说：

> 大副，从待办队列（backlog）里挑一件最近做完的活，按这一章流程图的顺序讲它实际是怎么走的：每一步对应流程里的哪一步，是你做的还是船员做的，哪些地方必须等我同意才能继续。不要改文件，也不要派船员，只讲已经发生的事。如果还没有做完的活，就直接说没有，然后挑最近的一件，讲它现在走到哪一步、下一步是什么。

**你应该看到**

- 按顺序讲：登记工单和写简报，派船员到独立工作树，质检流水线，开 PR 等你同意，合并，收尾清理。
- 每一步都说清是谁做的：分析、派工、监督、汇报是大副做的；改代码、跑流水线、开 PR 是船员做的。
- 指出哪里必须你拍板：至少是合并这一步；如果当时出现过 ask-user 类问题，那也算一处。
- 讲的是这件活真实发生的事，带着任务编号、PR 链接这类你能自己核对的信息，而不是把流程图再念一遍。

**怎么检查**

- 顺序和分工都对。特别是不能出现「船员自己决定合并」或「大副自己改了代码」这种说法。
- 明确说了合并需要你同意。
- 跟练习 1 一样，提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样。再看看有没有多出新的船员窗口，应该没有。

如果它讲的内容对不上任何一件真实的活，或者顺手去把那件活剩下的步骤做完了，就算没做成。
