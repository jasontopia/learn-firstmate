# 第 3 章：船员与隔离工作副本

## 这一章讲什么

第 1 章提到过一句话：船员是大副派出去的自主 agent，「一个船员一件活，每人一个可见的会话端点...和一份独立的 git 工作副本」。第 2 章讲完了一句话怎么变成一件可以派出去的活。这一章把镜头再往后挪一格，落在第 1 章流程图里「派出船员到隔离工作副本」这一关本身：为什么船员一定要在自己的一份 git 工作副本里干活，并行的多件活为什么不会互相踩，以及出事的时候，你和大副怎么去看一件活现在是什么状态。

本章依据的权威文件：`AGENTS.md` 第 1 节「硬规矩」、第 2 节「布局」、第 7 节「Intake and authority」「Dispatch and supervision handoff」两个小节，以及第 11 节（船员自验隔离）。每个小节会指出具体出处。

## 为什么每个船员要有自己的一份工作副本

先看第 1 节硬规矩第一条，原文是：「Never write to a project. Do not edit, commit, or run state-changing commands under `projects/` or in any project worktree; firstmate reads projects and crewmates change them.」

翻成大白话：大副从不写项目 - 不在 `projects/` 或任何项目工作副本下编辑、提交、或运行任何会改变状态的命令。这句话的后半句才是这一章的关键：大副读项目，**船员改项目**。真正动手改代码的，一直是船员，而且是在自己的工作副本里改。

第 2 节「布局」里给 `projects/` 下的定义呼应了这一点：「`projects/` contains clones that are read-only to firstmate except under hard rule 1's concrete captain-approved project operation exception.」`projects/` 里放的是一批克隆，对大副来说是只读的，只有硬规矩一里那条窄到具体某个项目、某个操作、且船长当场批准的例外能打破这一点。也就是说，`projects/` 本身对大副而言接近一份只读的项目登记，真正会被写入、被改动的，是从这些克隆里派生出来、专门为某一件活准备的工作副本。

这份专用工作副本从哪来，第 7 节「Dispatch and supervision handoff」写得很具体：「Spawn only through `bin/fm-spawn.sh` after the profile and backend checks in section 4. The spawn must resolve a genuine isolated task worktree distinct from the primary checkout; a failed isolation assertion stops the task.」

派工只能通过 `bin/fm-spawn.sh`，而且这一步必须解析出一份**真正独立于主检出目录**的隔离任务工作副本 - 隔离断言失败就直接中止这件活，而不是退而求其次改在主检出里干。这条断言不是走个过场：它把「船员的改动」和「大副操作的那份主检出」在物理上分开，硬规矩一「大副从不写项目」才有地方落地 - 如果船员的工作副本就是主检出本身，那大副稍不留神就会和船员的活撞在同一份工作树上。

第 1 章还提过一句，船员开机后会自己再验一遍这份隔离（`AGENTS.md` 第 11 节，由 `bin/fm-brief.sh` 的简报脚手架落实）：确认当前目录和 git 顶层目录都指向那份一次性的任务工作副本，而不是大副操作的那个主检出。写这一章的这个船员，动笔前做的第一件事就是这个：跑了一遍 `pwd -P` 和 `git rev-parse --show-toplevel`，确认两条命令报出来的路径一致，并且是一份跟主检出分开的一次性工作副本，才敢开分支、动笔写文件。这不是一句抽象的规矩，是这份文件本身写出来之前，真实发生过的一步。

## 为什么并行的多件活不会互相踩

工作副本隔离带来的直接好处，是并行不用靠「大家小心点」来维持。第 7 节「Intake and authority」原文：

「Treat file or subsystem overlap as a risk signal rather than an automatic reason to wait, and dispatch isolated work immediately with no concurrency cap when each change can be independently implemented and validated and the selected delivery path can reconcile ordinary rebases or conflicts. Serialize only for a true semantic dependency, shared mutable external state, incompatible concurrent migration, or another concrete condition that makes independent progress or reconciliation unsafe; same-file editing alone is insufficient, and genuine blockers remain durable.」

翻成大白话：文件或子系统重叠，只被当成一个**风险信号**，不是一个自动要排队等待的理由。只要每件活能够独立实现、独立验证，而且选定的交付路径能收敛得了普通的 rebase 或冲突，大副就会立刻派出隔离的活，不设并发上限。只有出现真正的语义依赖、共享的可变外部状态、互不兼容的并发迁移，或者其他让独立推进或事后合并变得不安全的具体条件，才需要串行 - 单纯「改的是同一个文件」不足以构成串行的理由，而真正的阻塞会一直挡在那里，不会不了了之。

这条规则之所以成立，正是因为工作副本隔离已经把「同一个文件被两件活同时改」这件事，从一个运行时问题变成了一个合并时问题。两个船员各自在自己的分支、自己的工作副本里改同一个文件，干活期间根本不会碰面 - 谁也看不见谁的改动，谁也不会覆盖谁的改动。这两份改动只会在合并这一步才第一次相遇，变成一次普通的合并冲突或者一次 rebase，跟平时多人协作用 git 处理冲突没有本质区别。真正会挡住并行的，从来不是「文件重叠」本身，而是重叠背后有没有第 7 节点名的那几种更硬的东西：一件活的结果是另一件活的前提（语义依赖）、两件活要共同读写同一份跑在别处的可变状态、或者两个互相不兼容的迁移同时在跑。

## 出事时怎么看

这份隔离还带来一个经常被忽略的好处：**看一件活现在是什么状态，不需要任何专门工具**。

原因是两条已经讲过的规矩叠在一起：船员一直在一份普通的 git 工作副本里干活（这一章第一节），而大副从不写项目、只读不改（硬规矩一）。结果就是，一件活在任意时刻的真实状态，都完整地留在它自己那份工作副本的 git 记录里 - 分支叫什么、有没有提交、提交里改了什么、跟它要合并的目标差多少。船长或者大副想知道一件活现在走到哪了，用的是最普通的 `git status`、`git log`、`git diff`，而不是某个只有 FirstMate 才认得的专有状态文件。出了问题要复盘，看的也是同一套东西：工作副本本身就是一份完整、诚实的记录，不会因为大副的调度层出了状况而跟着失真。

这本教程从第 1 章开始，验证「大副有没有改动」的办法就是前后各跑一次 `git status --short` 和 `git diff HEAD`（第 1 章「练习 1」）。这个验证方法本身就是这一章讲的道理在被反复使用：能拿最普通的 git 命令去核对一个 agent 到底有没有动过某份工作副本，前提正是这份工作副本一直只是一份普通的 git 仓库，没有任何隐藏状态。

## 动手练习

下面两个练习都是**只读**的：只是让大副读取信息、做推理并汇报，不会创建工单、不会派出真正的船员、不会改动任何被版本追踪的文件，也不会做任何不可回退的操作。你随时可以停下。

做练习前，先在你的 FirstMate 目录里启动一个 primary 会话，这样你面前的这个 agent 就是你的大副。

### 练习 1：讲清楚隔离断言卡的是什么

对大副说：

> 大副，给我讲清楚三件事：为什么每个船员干活都要有一份跟主检出、跟其他船员都不一样的独立 git 工作副本；这份独立工作副本如果解析不出来会怎样；以及为什么「两件活改的是同一个文件」本身不会让你自动把它们排成队串行。回答里指出你是根据哪个文件的哪一节说的。不要派任何船员，也不要改动任何文件，只回答。

**预期会看到什么**

- 它会区分「大副读项目、船员改项目」这条边界，并指出正因为改动都发生在船员这一侧，才需要把船员的工作副本和大副操作的主检出分开。
- 它会说清楚：派工必须解析出一份真正独立的隔离任务工作副本，解析不出来就直接中止这件活，而不是退而求其次在主检出里干。
- 它会讲到文件重叠只是一个风险信号，不是自动排队的理由；真正需要串行的是语义依赖、共享的可变外部状态、互不兼容的并发迁移这类更具体的条件。
- 它会指出出处，主要是 `AGENTS.md` 第 1 节、第 2 节，以及第 7 节 "Dispatch and supervision handoff" 和 "Intake and authority" 两个小节。

**怎么判断做成了**

三个都满足才算：三件事都讲到了，而且讲的是道理不是原文堆砌；它给出了可核对的出处；以及 - 最关键的 - 它**没有动任何被版本追踪的文件**，也没有派出任何船员，你可以直接看一眼有没有新开的会话窗口来确认。

文件层面的验证办法跟前两章一样，**前后对比**：提问之前先在 FirstMate 目录里跑一次 `git status --short` 和 `git diff HEAD`，把两份输出都留着；问完之后再各跑一次，两次应该完全一样。`data/`、`state/`、`config/`、`projects/`、`.no-mistakes/` 是大副私有的运行状态，被 gitignore 掉了，会话期间写这些不算数，这两条命令本来也看不见。

如果它把「文件重叠」直接讲成了一条必须排队的硬规矩，或者讲不出隔离断言失败会中止任务而不是降级处理，那就是没做成。

### 练习 2：只用 git 命令看一眼一件活现在的状态

对大副说：

> 大副，挑一件目前在办或者最近做完的活，只用普通的 git 命令 —— git status、git log、git diff 这类 —— 说清楚它现在是什么状态：分支叫什么、在不在一份跟主检出分开的独立工作副本里、有没有还没提交的改动、跟它要合并的目标差多少。不要用任何专门工具，也不要改动那份工作副本，只看和讲。如果眼下没有在办的活，就直接说没有，然后讲一遍如果有的话你会怎么看。

**预期会看到什么**

- 它报告的是**具体**的东西：分支名、工作副本路径是不是独立于主检出、有没有未提交的改动、离目标差几个提交或者有没有冲突 - 而不是抽象地说「一切正常」。
- 它用来得出这些结论的，全是普通 git 命令的输出，没有引用任何只有 FirstMate 内部才认得的专有状态。
- 如果它挑的是一件已经落地的活，它会说清楚现在还能不能看到这些记录（比如工作副本是否已经被归还清理），而不是编一个还在的说法。

**怎么判断做成了**

两条都满足才算：它讲的是一件具体活的具体状态，而且全程只用了普通 git 命令；以及 - 它没有去改动它正在查看的那份工作副本，也没有派出新的船员。

文件层面的判断跟练习 1 一样：提问前后各跑一次 `git status --short` 和 `git diff HEAD`，两次输出应该一样。

如果它讲的是一段泛泛的复述，或者干脆去补做了那件活剩下的步骤，那就是没做成 - 这个练习只要求它看和讲。
