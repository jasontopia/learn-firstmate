# 第 3 章：船员与工作树

## 这一章讲什么

第 1 章说过，每个船员 / crewmate 有自己的会话窗口和自己的工作树（worktree）。第 2 章讲了一句话怎么变成一件能派出去的活。这一章讲第 1 章的「第 2 步：派船员到独立的工作树」：为什么每个船员要有自己的工作树，几件活同时做为什么不打架，以及出了问题怎么查一件活现在的情况。

本章依据 FirstMate 仓库 `AGENTS.md` 第 1 节（硬规矩）、第 2 节（目录结构）、第 7 节的「Intake and authority」和「Dispatch and supervision handoff」两个小节，以及第 11 节。

## 为什么每个船员要有自己的工作树

硬规矩一说，大副 / firstmate 不改项目：不在 `projects/` 下或任何项目工作树里编辑、提交，也不运行会改变状态的命令。大副只读项目，改项目的是船员。

`projects/` 里放的是各个项目的克隆，对大副来说是只读的（硬规矩一里那条需要你当场批准的例外除外）。真正被改动的，是为某一件活单独准备的工作树。

派船员只能用 `bin/fm-spawn.sh`。派工时会做隔离检查：船员拿到的必须是一个真正独立的工作树，不能是大副自己用的主仓库目录。检查不通过，这件活就停下，不会退而求其次在主仓库目录里干。这样，船员的改动和大副用的主仓库目录分在两处，大副不会一不留神和船员改到同一个地方。

船员启动后还会自己再查一遍（`AGENTS.md` 第 11 节，由 `bin/fm-brief.sh` 生成的简报模板要求）：当前目录和 git 顶层目录都指向这件活专用的工作树，而不是主仓库目录。写这一章的船员，动笔前做的第一件事就是这个：运行 `pwd -P` 和 `git rev-parse --show-toplevel`，确认两者一致，而且是一个独立的工作树，然后才建分支、开始写。

## 几件活同时做，为什么不打架

`AGENTS.md` 第 7 节「Intake and authority」规定：几件活改到同一个文件或同一块代码，只算一个风险提示，不是自动排队的理由。只要每件活都能单独实现、单独验证，选定的交付方式也能处理普通的 rebase 和冲突，大副就马上把它们都派出去，不限同时做几件。

只有下面这些情况才需要一件一件来：

- 真正的依赖：一件活的结果是另一件活的前提。
- 两件活要读写同一份外部的、会变的状态。
- 两个互不兼容的迁移同时在跑。
- 其他让分头推进或事后合并变得不安全的具体情况。

光是改到同一个文件，不够成为排队的理由。但真正的阻塞仍然是要等的理由。

这条规矩能成立，靠的就是工作树隔离。两个船员在各自的分支、各自的工作树里改同一个文件，干活时互相看不见，也不会覆盖对方的改动。两份改动要到合并时才碰面，变成一次普通的合并冲突或 rebase，跟平时几个人用 git 协作一样处理。

## 出事时怎么查

工作树隔离还有一个好处：查一件活现在的情况，不需要什么专门工具。

船员一直在一个普通的 git 工作树里干活，大副又只读不改。所以一件活在任何时刻的真实情况，都完整留在它自己的工作树里：分支叫什么，有没有提交，提交改了什么，离要合并的目标差多少。你或者大副想知道一件活走到哪了，用普通的 `git status`、`git log`、`git diff` 就能看到。出了问题要复盘，看的也是这些。

第 1 章练习里检查大副有没有改文件，用的就是前后各跑一次 `git status --short` 和 `git diff HEAD`，道理相同：工作树就是普通的 git 仓库，没有藏起来的状态。

## 动手练习

两个练习都是只读的：只让大副读资料、推演、汇报，不登记工单，不派船员，不改被 git 追踪的文件。

开始前，在你的 FirstMate 目录里启动一个主会话，这个会话里的 agent 就是你的大副。

### 练习 1：讲清隔离检查管什么

对大副说：

> 大副，讲清三件事：为什么每个船员都要有一个独立的 git 工作树，跟主仓库目录和其他船员都分开；如果派工时拿不到这样的工作树会怎样；为什么「两件活改同一个文件」不会让你自动把它们排队。说明你依据的是哪个文件的哪一节。不要派船员，也不要改文件，只回答。

**你应该看到**

- 它讲到「大副只读项目，船员改项目」，并说明正因为改动都在船员那边，才要把船员的工作树和大副的主仓库目录分开。
- 它讲到拿不到独立的工作树，这件活就停下，不会改在主仓库目录里干。
- 它讲到改同一个文件只是风险提示，真正需要排队的是依赖、共享的外部状态、互不兼容的迁移这类具体情况。
- 说明出处：主要是 `AGENTS.md` 第 1 节、第 2 节，以及第 7 节「Dispatch and supervision handoff」和「Intake and authority」。

**怎么检查**

- 三件事都讲到了，而且是用自己的话讲道理，不是堆原文。
- 没有多出新的船员窗口。
- 跟第 1 章一样，提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样。

如果它把「改同一个文件」说成必须排队的硬规矩，或者说拿不到独立工作树时会退而求其次继续干，就算没做成。

### 练习 2：只用 git 命令查一件活

对大副说：

> 大副，挑一件正在做或最近做完的活，只用 git status、git log、git diff 这类普通 git 命令，说清它现在的情况：分支叫什么，是不是在一个独立于主仓库目录的工作树里，有没有没提交的改动，离要合并的目标差多少。不要用专门工具，也不要改那个工作树，只看和讲。如果现在没有正在做的活，就直接说没有，再讲讲有的话你会怎么查。

**你应该看到**

- 讲的是具体信息：分支名，工作树路径是不是独立于主仓库目录，有没有没提交的改动，离目标差几个提交、有没有冲突。不是一句「一切正常」。
- 这些结论都来自普通 git 命令的输出。
- 如果挑的是已经做完的活，它会说明这些记录现在还在不在（比如工作树已经收尾清理掉了），不会假装还在。

**怎么检查**

- 讲的是一件具体的活，而且只用了普通 git 命令。
- 没有改它查看的工作树，也没有派新的船员。
- 提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样。

如果它只是泛泛地讲一遍规则，或者顺手去把那件活剩下的步骤做了，就算没做成。
