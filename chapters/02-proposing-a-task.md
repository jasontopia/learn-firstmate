# 第 2 章：怎么提出一件活

## 这一章讲什么

第 1 章讲了一件活从提出到合并的全过程。这一章只看其中第 0 步到第 1 步：你说的一句话，大副 / firstmate 怎么把它变成一件能派出去、也能验收的任务。

这一步要定下好几件事：属于哪个项目，要一份报告还是要改项目，用哪种交付方式，谁有权同意合并，以及做成什么样才算做完。后面每一步都按这里定下的来。

本章依据 FirstMate 仓库 `AGENTS.md` 第 7 节的「Intake and authority」小节和第 11 节，以及 `bin/fm-project-mode.sh`、`bin/fm-brief.sh` 开头的注释。

## 大副要定的几件事

### 属于哪个项目

每次你提要求，大副都会重新判断它属于哪个项目：

1. 你点名了项目，就用它。
2. 这句话明显是接着上一件事说的，就沿用上一件的项目。
3. 都没有，就拿你的话去比对已登记的项目、正在做的活，以及项目的代码和 README。

只有一个项目明显对得上时，大副直接开始，并用平常的话告诉你选的是哪个。对得上好几个，或者一个都对不上，它就问你一个简短的问题，不会自己猜一个。

### 交付任务还是调研任务

- **交付任务（ship）** 是默认的，产出是对项目的改动，按选定的交付方式交付。
- **调研任务（scout）** 产出的是一份报告，放在 `data/<id>/report.md`，不开 PR。适合调查、诊断、规划、复现问题、审计这类工作，前提是你明确要一份单独的报告或设计，或者还有没弄清的问题，可能影响要不要做、做成什么样。

要注意：一个诊断请求、一份报告、一条建议，都只是参考信息，不等于同意改代码。你看完调研报告，还要再说一句「照着改」，才会进入交付。反过来，如果已有的报告或证据已经能回答你的问题，大副会直接告诉你，不会再派一次调研。第 6 章会细讲调研任务。

### 交付方式和合并权限

每件交付任务的交付方式和 `yolo` 开关，都在立项时就定好。派船员的 `bin/fm-spawn.sh`、把调研转成交付的 `bin/fm-promote.sh`，都要求明确传入这两个值，不会自己去猜。

交付方式有三种：

- **no-mistakes**：完整的质检流水线，最后开 PR，等有合并权限的人同意。这是默认的。
- **direct-PR**：不跑流水线，直接推送、开 PR，等有合并权限的人同意。
- **local-only**：只在本地分支上做，不推送、不开 PR。有合并权限的人同意后，大副用受保护的本地快进合并把它合进来。

`yolo` 开关跟交付方式无关，只管合并权限：关着，每次合并都要你同意；开着，大副可以自己合并 CI 全部通过、而且没超出任务范围的活。第 5 章会细讲。

这两个值按这个顺序定：你这次明确说了的，听你的；你没说，就用这个项目登记时定的设置；大副要用比登记设置更宽松的方式，必须说得出理由。项目没登记过，或者根本没有项目登记表，就用最严格的一档：`no-mistakes` 加 `yolo` 关着，并告诉你这个项目还没登记。

### 验收标准：写进任务简报

最后要定的是做成什么样才算做完。这一条写进派工前的任务简报（brief），分成两块：

- **船长意图**（Captain's intent）：你的原话和你提的限制，加上读懂这句话需要的背景。如果你提到了某份报告、某个决定或某个 PR，要把里面的具体内容写进来，不能只留一个链接。
- **大副规格**（Firstmate spec）：具体怎么做。这一块不算船长意图。

两块分开写，是因为质检流水线拿「船长意图」当验收标准。所以大副不会在这一块里把你的要求扩大成一个笼统的目标。派工命令也会拒绝还有空白没填的简报。

## 怎么说能少走弯路

把上面几件事反过来看，就是你这边能做的：

- **说出项目名，或者让这句话明显接着上一件事。** 这样大副不用再问你是哪个项目。
- **说清楚要报告还是要改东西。** 「帮我看看」和「去把它实现了」是两条路：一个产出 `data/<id>/report.md`，一个产出项目改动和 PR。你自己也没想好要不要做，大副会问你，不会先动手。
- **想用跟项目登记设置不同的交付方式或合并权限，就明说，并给个理由。** 你不说，就按登记的来。比如「这次直接开 PR，不用走完整流水线」，再加一句为什么。
- **提到某份报告、某个决定或某个 PR 时，把相关的内容说出来。** 验收只认写进简报的内容，只给一个链接，流水线看不到背景。
- **涉及合并、破坏性、不可逆或安全的操作，说清楚具体要做什么。** 这类事最后总要你来定，一句「你看着办」不算授权。

## 动手练习

两个练习都是只读的：只让大副读资料、推演、汇报，不登记工单，不派船员，不改被 git 追踪的文件。

开始前，在你的 FirstMate 目录里启动一个主会话，这个会话里的 agent 就是你的大副。

### 练习 1：用一句含糊的话测试立项判断

对大副说：

> 大副，我想看看你立项时怎么判断，不是真要你干活。假设我只说了一句：「东西好像有点不对劲，帮我看看」，没说是哪个项目，也没说要报告还是要改。请按你平时立项的步骤讲一遍：你怎么判断属于哪个项目，归成交付任务还是调研任务，会不会先问我，问的话问什么。只推演，不要登记工单，也不要派船员。

**你应该看到**

- 它指出这句话判断不出项目：没点名，也不是接着哪个项目说的。
- 它说会先问你一个简短的问题，而不是自己挑一个项目往下做。
- 它指出「帮我看看」也没说清要报告还是要改，这一点同样要先问清楚，或者至少点出来。
- 说明出处：`AGENTS.md` 第 7 节「Intake and authority」。

**怎么检查**

- 它讲清了为什么要先问你，而不是替你猜一个项目。
- 没有登记工单，也没有多出新的船员窗口。
- 跟第 1 章一样，提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样。

如果它没问就自己挑了项目往下做，或者把这句话当成了动手改的授权，就算没做成。

### 练习 2：对照一件做完的活，看它立项时定了什么

练习 1 是假设的情况，这次看一件真实做完的活。这本教程所在的仓库就有现成的例子：写第一章的那件活，以及给仓库加 CI 检查的那件活。

对大副说：

> 大副，挑这个仓库做完的一件活，比如写第一章《FirstMate 是什么》那次，或者给仓库加 CI 检查那次。讲讲立项时定下了什么：怎么判断它属于这个项目，是交付任务还是调研任务，用的是 no-mistakes、direct-PR 还是 local-only，`yolo` 开没开，船长意图里的验收标准大致是什么。如果记录已经找不到了，就直接说找不到、为什么，不要编。不要改文件，也不要派船员，只讲已经发生的事。

**你应该看到**

- 讲的是其中一件真实的活，带着你能自己核对的信息，比如 PR 链接或提交记录。
- 分开讲清项目、任务类型、交付方式、`yolo` 开关、验收标准这几项，而不是笼统一句「按规矩走的」。
- 如果当时的工单记录或简报已经找不到（比如清理过，或者已完成的工单只保留最近几条），它会直接说找不到并说明可能的原因，不会编一段「船长意图」出来。

**怎么检查**

- 讲的是能核对的真事，不是复述规则。
- 找不到记录时承认找不到。
- 提问前后各跑一次 `git status --short` 和 `git diff HEAD`，输出应该一样，也没有多出新的船员窗口。

如果它把这次提问当成一件新活去立项，或者在找不到记录时编了一段验收标准，就算没做成。
